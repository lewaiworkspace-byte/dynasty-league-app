## 1. Hardcoded to exactly 10 teams

**Method.** I grepped `app/`, `components/`, `lib/` and `middleware.js` for `10`, `ten`, `tenth`,
`10th`, `9`, `nine`, phrases like "of ten", "all ten" and "other nine", and named constants
(`TEAM_COUNT`, `numTeams`, …). I then read every hit in context and separated real assumptions from
the many uses of 10 that have nothing to do with teams.

**The rule this measures against.** `.claude/rules/ui-patterns.md`: *"Text an owner reads never
states the number of teams as a literal. Count the rows the page loaded, or name no number."*

### 1A. Rendered to owners (breaks the rule above)

**F1-1: `app/team/[teamId]/page.js:1008`.** The RECORD tile on Team HQ builds its note as

```js
standingsRow.league_rank + ' of 10 · ' + standingsRow.points_for + ' PF'
```

The `10` is a literal. With any other number of teams it prints a wrong denominator, and nothing
flags it. The page reads only this team's standings row (`:459-462`), so it has no count of its
own to use. A fix would either count the season's `league_standings` rows or drop the "of N".
(The `StatTile` doc comment at `components/ui/StatTile.js:4,16` uses "8th of 10" as an example.
That is a comment, but it shows the same pattern.)

**F1-2: `app/free-agency/FreeAgencyBoard.js:619`.** The sealed-offers notice tells owners a count
is never shown *"because in a ten-team league a count would say who."* This is rendered JSX text,
not a comment. The reasoning comes from ruling FA-D and would still hold at another league size;
only the literal needs to go (e.g. "in a league this size").

### 1B. Logic tuned for a ten-team league

**F1-3: `app/team/[teamId]/page.js:695`.** On the Media tab,
`supabase.from('teams').select('id, name, abbrev').order('name').limit(20)`. At 20 teams this
works; past 20 it silently drops teams alphabetically, with no warning. It's a hidden cap on
league size, and it is not a "bound-and-warn" read as `data-fetching.md` defines one.

**F1-4: `app/bids/TierPlayerList.js:58-61`.** `INTEREST_BANDS` marks a player "Highly
competitive" at 6+ bids and "Heating up" at 3+. Each team bids once per player, so these
thresholds are fractions of a ten-team league (6 of 10, 3 of 10), and they'd mean something
different with another team count. The bands come from the commissioner ruling of August 13, 2026
(comment at `:45-56`), so changing them is a ruling question, not a code fix. Listed so the
dependency is on record.

### 1C. Row-ceiling decisions that depend on "ten teams" (F1-5)

## 2. `.select()` reads with no `.range()` that could exceed 1,000 rows

**Method.** The repo has 276 `.select(` calls in `app/`, `components/` and `lib/`. A small script
pulled out the full query chain around each one (from `.from(`/`.rpc(`/`.insert(` to the end of
the statement) and tagged it for `.range()`, `.single()`/`.maybeSingle()`, `.limit()`,
`head: true`, and writes. Results:

| Tag | Count |
|---|---|
| no `.range`, `.limit` or `.single` | 148 |
| `.single()` / `.maybeSingle()` | 74 |
| `.limit(n)` only | 29 |
| `.range()` in the chain | 16 |
| write-returning (`.insert().select()` etc.) | 6 |
| `head: true` count | 3 |

I then read all 148 by hand. Many look unbounded but aren't: their builder is passed to a pager
that calls `.range()` (`fetchAll`/`fetchIn` in `lib/dataExports.js`, `fetchAllPages` in
`lib/statsHelpers.js`, `fetchAllRows` in `app/trades/page.js` and `app/trades/new/page.js`), or
the ids arrive in 100-id chunks. The appendix gives a verdict for every one of the 148.

**The rule this measures against.** `.claude/rules/data-fetching.md`: page-until-exhausted for
anything that must be complete; bound-and-warn (explicit `.range()` plus a visible notice) for a
ledger a human scrolls.

### 2A. Can exceed 1,000: the set grows without limit

**F2-1 (High): `app/admin/fix-contracts/page.js:19-22`.**

```js
supabase
  .from('contracts')
  .select('id, player_id, team_id, contract_type, status, start_year, total_years, void_years, signing_bonus_total')
  .order('start_year', { ascending: false }),
```

- **No filter.** It reads every contract of every status, ever, and that set only grows.
- **No `.range()`.**
- **Non-unique order.** `start_year` ties for most rows, so once the read is truncated, *which*
  contracts drop out is not even stable between loads.
- **The players lookup grows with it.** The follow-up at `:41-44`
  (`players … .in('id', playerIds)`) carries one id per distinct contracted player. Past 1,000 it
  is truncated too, and long before that the `in.(…)` list makes a very long request URL.

The comment at `:27-35` explains the fix for an earlier bug (reading the whole `players` table)
and says the scoped lookup "can't hit that ceiling". That is true of the old bug, but the
`contracts` read it depends on is itself unbounded. This is an officer repair tool, so a contract
past the cap simply never appears to be repaired. It needs page-until-exhausted (it must be
complete), ordered on `id`, and the players lookup chunked the way `fetchIn` does it.

**F2-2 (Medium–High): `app/admin/trades/page.js:72-83`.** The queue holds up to
`QUEUE_LIMIT = 200` trades with status `accepted` or `executed`. Executed trades stay in that
status, so the queue fills toward 200 over time. For those ids it reads `trade_parties` and
`trade_assets` with no `.range()` and **no `.order()`**. Two parties and a few assets per trade
reaches 1,000 well within 200 trades. `app/trades/page.js:217-228` pages exactly these two reads (comment at `:29-33`),
and says why: *"a truncated asset list would silently mis-state what a trade contains."* The
officer page is the one where that matters most, because it is where a trade gets executed,
vetoed or reversed. It also ignores the `error` on both reads (`{ data: parties }`), so a failure
would show as trades with no assets.

**F2-3 (Medium): `lib/restructureRoster.js:67-76` and `:88-94`, reached with `teamId = null`
from `app/admin/restructure/actions.js:51`.** With no team filter, it reads every `active`
contract in the league, unpaged, then `contract_year_computed` for those ids (one row per
contract for the season, also unpaged, and again a long `in.(…)` list). The total is capped by
roster limits × team count, so it is probably under 1,000 at today's size. Two code comments put
active contracts at "233" (`app/trades/new/page.js:14`) and "290"
(`app/admin/cuts/page.js:81`). Neither is verified, and they disagree. `app/trades/new/page.js`
pages the same `contracts … eq('status','active')` read. This one should match.

**F2-4 (Low–Medium): `app/bids/results/[tierId]/page.js:82-86`.** It reads `auction_tier_results`
for the tier, unpaged. Per the Database Reference (§3, column list) that view has one row per bid,
so a tier yields about players × teams bidding. The same file pages
`auction_tier_result_years`, and the export route
(`app/bids/results/[tierId]/export/route.js:20-35`) pages **`auction_tier_results` itself**. So
the published page and its download can disagree for a big enough tier. Ordered by `player_name`
only, which is not unique.

**F2-5 (Low): name lookups built from trade lists.** `app/trades/page.js:252-258` and
`app/admin/trades/page.js:95-101` read `players … .in('id', playerIds)` and
`draft_picks … .in('id', pickIds)` without paging, using the distinct ids from up to 200 trades'
assets. Going past 1,000 distinct players across 200 trades is unlikely, but nothing bounds it,
and a truncated lookup prints "Draft pick" or a missing name instead of an error. (In the admin
file this follows F2-2's already-truncatable asset list.)

**F2-6 (Low, accepted risk): `app/draft-picks/page.js:58-65`.** `draft_pick_board`, every
season, unpaged. Per the Database Reference (§3), the view is *"One row per pick, every season in
`draft_picks`."* The comment at `:30-36` records this as a deliberate decision. Code comment says
250 rows, growing 40 a season, reaching 1,000 "around the 2045 draft". Listed because it is
literally unbounded, and because its growth rate scales with team count (§1C). If the league
grows, the date in that comment moves closer.

**F2-7 (Very low): lists that span every season.** `app/bids/page.js:212` (every verified
auction tier), `app/admin/tier-results/page.js:28` (every tier), `app/values/page.js:35` (every
published value snapshot). Each grows by a handful of rows a season. No action needed, but they
are unbounded by construction.

### 2B. Explicit bounds at or past the ceiling (adjacent to scope)

These have a bound, but the bound doesn't do what it looks like it does.

**F2-8a: `app/league-finances/page.js:73-76`.** `.limit(1000)` on a season's `league_fines`,
with no truncation notice. `data-fetching.md` says a bare `.limit(n)` is "neither pattern".
This one sits exactly at the ceiling, so a 1,001st fine would drop silently. Unlikely to happen
(see §1C), but it isn't bound-and-warn.

**F2-8b: `app/library/page.js:29-32`.** `.range(0, 4999)` on `library_feedback_feed`, used to
count feedback per document. PostgREST's `max-rows` caps the response no matter how large the
requested range. If this project uses Supabase's default of 1,000, the badge counts undercount
silently past 1,000 items. **The Database Reference does not record the project's `max-rows`
setting**, so I can't confirm the effective cap. A re-cut could include it.

### 2C. Bounded by the number of teams (safe at today's size)

Twenty-two reads return one row per team, or one row per team for a season: every bare
`from('teams')` (14 sites plus `lib/dataExports.js:156`), `team_cash_available` /
`team_cap_summary` / `league_standings` filtered to one season, `team_inseason_compliance`, and
`team_owners` (`app/admin/owner-activity/actions.js:90`). They are all safe as long as the league
is small. Together with §1C, they are the full list to re-check if the league ever grows.

### 2D. Paged, chunked or scoped to one entity (no action)

- **Paged:** all 31 `fetchAll` chains in `lib/dataExports.js` (it pages until a short page,
  `PAGE = 1000`); `lib/statsHelpers.js:127-142` (`fetchAllPages`); `app/trades/new/page.js:40-64`
  and `app/trades/page.js:217-228` (`fetchAllRows`). I spot-checked their order keys: each is the
  row's id or a composite that is unique under the read's own filter (e.g.
  `['player_id','season_year']`, `['season_year','week_number','matchup_id']`, `['log_id']`).
  Whether each view's key really is unique is a database fact the Reference states only for some
  views (e.g. `league_transaction_log`, "page on `log_id`").
- **Chunked:** `players` lookups in 100-id chunks (`app/free-agency/actions.js:105-118`,
  `app/waivers/actions.js:51-63`, `lib/statsImport.js:341`).
- **Scoped:** 35 reads filtered to one player, trade, bid, tier + team, waiver run, team or
  snapshot. `app/values/page.js:81` reads one snapshot (code comment says 500 rows each; the
  comment at `:15-21` records why it must never go unfiltered).
- **Config:** `ppv_weight_table`, `league_cap_settings`, `bid_interest_levels` (4 rows per the
  Reference), `goodell_kinds`, calendar and week tables filtered to one season.

### 2E. Out of scope but related: RPCs

The repo makes 123 `.rpc(` calls. PostgREST applies the same `max-rows` cap to a set-returning
function. This audit covered `.select()` only, as asked. Checking which RPCs return sets that
could pass 1,000 rows would need the Reference's §4 return types and is a separate pass.

## Things noticed in passing (not in scope, not acted on)

- **Long `in.(…)` URLs.** F2-1, F2-3 and F2-5 pass hundreds of UUIDs in one `.in()`. Each UUID
  adds about 37 characters to the request URL. `lib/dataExports.js` (150 per chunk) and the
  waiver and free-agency lookups (100 per chunk) chunk for this reason.
- **Swallowed read errors.** `app/admin/trades/page.js:72-83` and `:95-101`, and
  `app/admin/fix-contracts/page.js:18-24, 41-44`, destructure `{ data }` only. A failed read
  renders as an empty list or "Unknown player", which `money-and-dates.md` ("A blank must never
  read as compliant") warns against.
- **Bound-but-silent `.range()` reads.** `app/admin/cuts/page.js:63` (`cut_history`,
  `range(0, 499)`) and `:94` (`range(0, 999)`) have a bound. I didn't check whether each shows the
  truncation notice that bound-and-warn requires. The `:94` read uses all 1,000 rows of the cap.
